## Performance

> Manual old-vs-new benchmark of the `--columnar` engine over the set in [`columnar_wip/benchmark-networks.md`](columnar_wip/benchmark-networks.md). This is **not** the CI `perf-pr.yml` check, which only sees the default OO path since the new core is flag-gated.

Single-threaded (`MODE=release OPENMP=0`), `--seed 123`. Codelength in bits. **`instr` is instructions retired** (`/usr/bin/time -l`). `time` is `--timing-json`'s `timing.total_s`.
- `-N10` rows run once (deterministic; `instr` carries the comparison).
- `-N1` rows are the interleaved minimum of 3.
- Drivers: [`columnar_wip/bench-1140.py`](columnar_wip/bench-1140.py) for every configuration #1136's snapshot had, writing [`columnar_wip/1140-ab-results.tsv`](columnar_wip/1140-ab-results.tsv), and [`columnar_wip/bench-1140-controls.py`](columnar_wip/bench-1140-controls.py) for the family rows #1158 added, writing [`columnar_wip/1140-controls.tsv`](columnar_wip/1140-controls.tsv).
- The tables are built from [`columnar_wip/1140-snapshot.tsv`](columnar_wip/1140-snapshot.tsv), which [`columnar_wip/combine-1140-snapshot.py`](columnar_wip/combine-1140-snapshot.py) writes, by [`columnar_wip/assemble-hier-gaps.py`](columnar_wip/assemble-hier-gaps.py).

> **This PR changes when the objective-option warnings fire, and nothing the engine computes (F67).**
> - `--entropy-corrected` and `--preferred-number-of-modules` warned "has no effect on this run" under `-C` on state, multilayer and meta-data input, while the columnar engine applied both: states.net `-C` went from 2.011405238 to 2.169200009 bits under `--entropy-corrected`, next to a warning that it reported the uncorrected codelength.
> - The check now asks the engine that runs. The one `-C` run that is scored by the object-oriented objective, `--no-infomap` without an input partition, still warns, and only about the entropy term.
> - Both checks run once per run, before the trials, and touch nothing the search or the scoring reads. So this snapshot is here to show that nothing moves.

> **Old** = a fresh `MODE=release OPENMP=0` build of `columnar-hierarchical-core`, md5 `eddfdee90cfa3f43227d53b848af8821`. It was measured as tip `501f523a`; the tip is now `d5e32d85` (#1158), which changes nothing under `src/`, and a clean build of it gives the same md5. **New** = this PR at `78d58569`, md5 `acb26dc549cf3f155b8dbd00f29c0d88`, built clean the same way; merging #1158 in changes no source either.
> - **Two sessions, both arms interleaved per row with the first arm alternating.** `-N1` rows are the minimum of 3 reps spread across the batch, and `-N10` rows run once.
>   - **2026-10-11:** every configuration of the #1136 snapshot. Load spikes from other work on the machine inflated some cells by up to 7.9× in seconds, so two more rounds re-measured both arms of every cell the load had distorted: the 22 where new first read more than 3% slower (3 extra reps, and 4 more for the two still above +3%), and 18 that ran more than 15% slower than #1136's time for the same source or read more than 5% faster (5 extra reps). A cell is the minimum over its reps, 1 033 runs.
>   - **2026-10-13:** the 37 family configurations #1158 measured (its 30 new rows and the seven plain planted rows it re-scored), 222 runs. Every planted row comes from this session, so each block's one-level codelength does too.
> - **A different machine from the snapshots before #1140, with the same source:** the old column reproduces #1136's new column in bits, top modules and levels on all 177 configurations of the first session, and #1158's values on all 37 of the second. The first session ran at 0.991× #1136's seconds (median over 341 cells of at least 0.05 s, quartiles 0.96–1.02); the second, quieter, at 0.864× #1158's.
> - **Load** was 2.4–165.5 in the first session (1-minute average at each run's start, median 7.8) and 4.6–6.0 in the second, so read `instr` before `time` in the first.
> - **OO arms:** the OO engine is untouched, so its cells are carried from the #1158 snapshot, which has them as #1136 did. The first session runs the same source as fast as those machines (above), so the OO-vs-columnar seconds still compare.
>   - OO `air30k (meta)` `-N1` on seed 123 still has no number: it ran for 9 h 25 min and was killed (#1134).

### What the change moves

Nothing. All 207 configurations the tables show are bit-identical between the arms in bits, top modules and levels, on every run of both sessions, so the table below has no rows.
- **Instructions:** −2.53% to +0.60% (median −0.03%). Every cell beyond ±0.3% is a row under 0.07 s, where process start-up is a large share of the count: multilayer, ninetriangles, netscience, jazz and lazega. One arm's reps spread about as much on a long row: the eight old runs of om3_N256_E50k `-d -N10` span 42.66–42.74 G.
- **Seconds:** −29.0% to +6.0% (median −0.17%). 47 cells read more than 1% slower and 55 more than 1% faster (below).

**Every cell where new is worse than old, and why.**

No cell is worse in bits. In seconds, 47 of the 207 cells read more than 1% slower, at −0.96% to +0.30% in instructions, and 55 read more than 1% faster. Nothing in the change runs during the search: it adds two checks of a few comparisons each, once per run, before the trials. The largest:
- **om3_N256_E50k `-d`, `-C -N10`: +6.0%** in seconds as the minimum of 8 reps per arm, at +0.03% in instructions. One old rep took 4.16 s, 6% below every other run of either arm (4.42–4.63 s). The medians are 4.50 s (old) and 4.49 s (new).
- **The planted rows of om2_N256_E100k and om2_N256_E50k: +4.5% and +3.9%** in seconds, at +0.09% and +0.15% in instructions, on 0.05–0.06 s rows in the quiet second session.

The other 44 are at +1.0% to +2.8% in seconds.

### The overlapping family in full

Every configuration of the planted overlapping state networks: om2–om8 on N = 256 physical nodes at

partition, scored with `-2d --no-infomap -c` under the block's objective. Then come the four searches.
- **Δ vs planted** is the new search's codelength against that planted partition, **bold** where the
  search is worse.
- On a planted row it is the planted partition against one-level instead. Where that is **bold** the
  planted partition is worse than one-level: it is no reference, and the block's deltas are ~~struck~~.
- The plain search rows are the same runs as the `-C`, `-C -2` and `-C -N1` rows of that network. The
  planted rows, the plain `-2d -N1` rows at the second density and om2_N256_E100k's regularized `-N1`
  rows come from the second session.
- Every row is bit-identical, so each delta is the same in both arms.
