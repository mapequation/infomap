## Performance

> Manual old-vs-new benchmark of the `--columnar` engine over the set in [`columnar_wip/benchmark-networks.md`](columnar_wip/benchmark-networks.md). This is **not** the CI `perf-pr.yml` check, which only sees the default OO path since the new core is flag-gated.

Single-threaded (`MODE=release OPENMP=0`), `--seed 123`. Codelength in bits. **`instr` is instructions retired** (`/usr/bin/time -l`). `time` is `--timing-json`'s `timing.total_s`.
- `-N10` rows run once (deterministic; `instr` carries the comparison).
- `-N1` rows are the interleaved minimum of 3.
- Driver: [`columnar_wip/bench-sync.py`](columnar_wip/bench-sync.py), writing [`columnar_wip/sync-1162-ab-results.tsv`](columnar_wip/sync-1162-ab-results.tsv). One session, old and new on every row of the #1163 snapshot, on both engines.
- Tables: [`columnar_wip/assemble-hier-gaps.py`](columnar_wip/assemble-hier-gaps.py) builds every table from the TSV that [`columnar_wip/tables-1042.py`](columnar_wip/tables-1042.py) `assembly` writes, now including the OO cells. The REG table comes from `tables-1042.py reg`.

> **This PR syncs master into the branch: 54 commits since #1077, through #1162** (merge `b4524f2f`).
> - **The columnar search is untouched.** All 332 columnar configurations are bit-identical, old against new: `-C`, `-C -2`, `-C -N1`, `-F`, `--non-redundant`, the overlapping family and the REG rows. Master's two flow fixes do not reach the benchmark set: #1149 changes only regularization strength 0, and #1162 only networks with parallel self-links.
> - **Its one cost is master's input fingerprint ([#1167](https://github.com/mapequation/infomap/issues/1167)).** Since #1096 every run hashes each input file byte by byte, about 7.7 instructions per byte: +12M to +23M instructions on an om input, +177M on web-NotreDame.
>   - On the planted `--no-infomap -c` rows, which only score a partition, that is +1.3% to +2.3% in instructions. On searches it is +0.11% (median).
>   - It is the whole cost. Over the 296 columnar configurations above 0.3G instructions, subtracting 7.7 instructions per input byte leaves a median of −0.000% (5th–95th percentile ±0.11%).
>   - A throwaway build with the hash gated off is back at the old count: om5_N256_E100k planted −0.24% (old +1.98%), web-NotreDame `-C -N1` −0.00% (old +0.68% in instructions, +1.9% in seconds).
>   - The code is shared, so the fix belongs on master.
> - **The object-oriented search moves, all of it from #1142**, which stops the aggregation loop at the first pass that merges nothing. 14 of 28 OO configurations change, from −0.008% to +0.046% in bits. Summed over the 28: −0.68% in instructions, −1.08% in seconds. See [the OO table](#old-vs-new-object-oriented).
> - **OO air30k (meta) finishes now.** It is #1134, closed by #1142: 8.2434 bits at `-N10` in 24.9 s, and 9.2255 bits at `-2 -N10`. It is no comparison for the columnar row: on metadata over higher-order input the two engines deliberately optimize different objectives (F39, #1012). The columnar engine adds the metadata term to the full higher-order objective; OO scores state nodes only, without the physical-node codebook. Without `--meta-data` both engines price both partitions identically. See [OO vs columnar](#oo-vs-columnar).
>
> Measured in one session, 2026-10-14.
> - **Old:** a fresh build of the branch tip `aa4f8689` (#1163), md5 `ccc09e195323b7bfa946f0de317c9179`. This is byte-identical to #1163's new arm, and this session reproduces that one: all 332 columnar codelengths are equal, and instructions agree to a median +0.02%, every row above 0.3G within ±1%.
> - **New:** this PR's merge `b4524f2f`, md5 `8ee83b9936fe3c20a54754724f56b87e`.
> - **OO arms** are measured, not carried, because a sync changes the OO engine too. They run on the 14 networks of the two OO tables, minus air30k (meta), whose old arm cannot finish (#1134). That row's new arm ran alone right after the sweep.
> - **Load:** 1-minute load 9–19, with an unrelated single-threaded job on one core throughout. Seconds read about 3% above #1163's session on identical code (median over rows of at least 0.1 s), so `instr` is the steadier axis. The arms are interleaved per row; `-N1` rows are the minimum of 3 reps spread across the batch.
> - **Family rows** that repeat a `-C`, `-C -2` or `-C -N1` row take that row's run, so the two tables agree.

### The overlapping family in full

Every configuration of the planted overlapping state networks: om2–om8 on N = 256 physical nodes at
E = 50k and 100k trigrams (F55), under both objectives (F66). Each block of five starts with its planted
partition, scored with `-2d --no-infomap -c` under the block's objective. Then come the four searches.
- **Δ vs planted** is the new search's codelength against that planted partition, **bold** where the
  search is worse.
- On a planted row it is the planted partition against one-level instead. Where that is **bold** the
  planted partition is worse than one-level: it is no reference, and the block's deltas are ~~struck~~.
- The plain search rows are the same runs as the `-C`, `-C -2` and `-C -N1` rows of that network.
- Every row is bit-identical. The planted rows pay #1167's fingerprint, +1.3% to +2.3% in instructions:
  scoring a partition is cheap, so hashing the network and the `.clu` is a visible share of it.
