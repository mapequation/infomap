## Performance

> Manual old-vs-new benchmark of the `--columnar` engine over the set in [`columnar_wip/benchmark-networks.md`](columnar_wip/benchmark-networks.md). This is **not** the CI `perf-pr.yml` check, which only sees the default OO path since the new core is flag-gated.

Single-threaded (`MODE=release OPENMP=0`), `--seed 123`. Codelength in bits. **`instr` is instructions retired** (`/usr/bin/time -l`), taken from the *same execution* as the wall time and reported because it is load- and clock-independent. `time` is `--timing-json`'s `timing.total_s`: **one run per `-N10` row** (the codelength is deterministic and `instr` carries the comparison) and **interleaved minimum of 3 for `-N1` rows**.

> **This PR is the master sync**, bringing [#1044](https://github.com/mapequation/infomap/pull/1044) through [#1066](https://github.com/mapequation/infomap/pull/1066) onto the branch — the `linlog` damping interpolation's smoothness at `q = 1`, the one-level reference and the tree-level `|K − K_pref|` cost ([#1052](https://github.com/mapequation/infomap/pull/1052), [#1054](https://github.com/mapequation/infomap/pull/1054)), the clu and output-artifact fixes, the effective seed in the default artifacts, and the dependabot bumps. **It contains no columnar search change**, so the claim these numbers exist to test is a negative one: *the columnar engine must be bit-identical to the tip everywhere*. It is — **125 of 125 columnar configurations agree to the last digit**. What moved is the object-oriented arm, on the one row master aimed at.
>
> The one columnar code change is a reconciliation, not a search change. #1052 gave `--preferred-number-of-modules` an object-oriented counterpart inside `calcCodelengthOnTree`; the columnar engine's ragged-tree fallback had been adding that penalty by hand *because no counterpart existed*, so after a clean, conflict-free merge both charges applied and `infomap_cpp_non_redundant_tests` failed 5 of its 6 checks. The two are also not the same charge — master counts K at `root.childDegree()` (top modules), the columnar engine at `hierLevelSize(1)` (leaf modules) — so the fallback now subtracts the object-oriented term and adds its own, leaving each engine the answer it gave before. Which level *should* own K is [#1068](https://github.com/mapequation/infomap/issues/1068), decided (top modules) but deliberately not implemented here; see F52.

> **Where it costs — one inherited regression, and it is master's.** Five rows are more than 1% worse in instructions with **no change in bits**: the `om* planted, --no-infomap -c` rows, at **+7.0 to +7.5% instructions** (+3.2 to +7.5% in time), and `om2 -2d -c` at +1.02%. Every one of them passes `-c`; the 40 overlapping rows that do not are unaffected (median −0.2M instructions). The cost is linear in the cluster file's row count at **~2 290 instructions per row with an intercept of zero** — one extra pass over the file — and that is exactly what it is: [#1051](https://github.com/mapequation/infomap/pull/1051)'s `reportClusterDataIssues` parses `--cluster-data` a second time to warn about repeated node ids, as its own comment says ("The cost is one extra parse of the cluster file, which is a validation pass and not the partition the trials build"). It is once per run, so it is worst where the run is shortest: 7% of a `--no-infomap` scoring run, ~1% of a `-N10` search seeded with the same file, nothing on a long search. Filed as [#1072](https://github.com/mapequation/infomap/issues/1072) — the duplicate statistics are already computed by the run's own read, so the second pass looks avoidable. **A hypothesis was killed on the way**: the obvious suspect, #1051's per-row `try_emplace` bookkeeping, was gated off in a throwaway build and the +120M did not move.
>
> **The two rows that changed in bits are both object-oriented `science2001 (pref.)`, and both are #1052/#1054 working as intended:**
>
> | row | bits | instructions | time |
> |---|--:|--:|--:|
> | OO `-d --preferred-number-of-modules 25 -N10` | 7.940353597 → **7.938575228** (−0.0224%) | 65.27G → 57.17G (**−12.40%**) | 8.12s → 6.98s (−14.09%) |
> | OO `-2d --preferred-number-of-modules 25 -N10` | 8.130969526 → **8.131110023** (**+0.0017%**) | 44.36G → 37.09G (**−16.39%**) | 5.94s → 4.97s (−16.47%) |
>
> The `-N10` row is better in bits *and* 12% cheaper. The `-2` row is the only cell in the sweep that is worse in bits: **+0.0017%, fifty times under the 0.1% reporting bar, bought with 16.4% fewer instructions** — a search-path change, not a modelling loss, and master's to own rather than this branch's. Both keep `top = 25`, so the bias is still doing its job. The columnar arms of the same three configurations are bit-identical with instruction counts equal to three significant figures (35.76G, 31.70G, 5.88G on both sides), which is what makes their ±1.4% time wobble demonstrably noise.

> **Read the time column against the instruction column.** Across the 125 columnar configurations the median instruction delta is **+0.005%** (5th–95th percentile −0.14% to +0.93%) while the median time delta is +0.19% (−1.99% to +4.88%). Every columnar row more than 2% worse in time except the five `planted` ones sits at ~0% in instructions — `politicalblogs -2` reads +10.79% in time against **−0.04%** in instructions, `om5 -d --regularized -N10` +4.88% against **+0.02%**. Those are the machine, not the code. The sweep ran at 64–78% idle, both arms interleaved with reps spread across the batch rather than bursted, and the small startup-dominated rows carry 5 interleaved reps each after the first pass showed the sweep's very first run had paid cold-start costs (`ninetriangles -C -N10` read 403M instructions against 80M on every warm repeat — an artifact, now gone).

> **Old** = a fresh build of the `columnar-hierarchical-core` tip `090d9ab9`, md5 `4b63cea29119bc7623e7a5385ccf6388`; **new** = this PR, md5 `87a420d771279897311dbddf6b126e78`. The branch picked up two further merges after the sweep — the columnar tip's `0de361f8` (a ruff fix to `prune-probe.py`) and master's #1059 (python binding docs) — and neither touches `src/`: a clean rebuild of the final tree reproduces that md5 byte for byte, so these numbers describe the branch as it stands rather than an earlier state of it. Both built `MODE=release OPENMP=0` from clean trees and interleaved in one session (492 runs, 0 errors). The old arm's md5 is the same binary the previous PR shipped as its "new", which is the tip by construction. **Unlike the previous snapshot, the OO arm is re-measured rather than carried from the log** — a master sync can move the object-oriented path, and here it did.
